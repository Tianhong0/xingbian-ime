#### 多候选的实际组织方式（重要，与常见假设不同）

**同一码点不会跨行重复。** 实测：

- 数据行 **88 937**，唯一码点 **88 937**，**重复码点 0 个**。
- 多来源候选是**放在同一行的第 3 列之后**，用 `\t` 分隔，而不是拆成多行。

字段数直方图：

| 字段数 | 行数 | 含义 |
|---|---|---|
| 3 | 85 435 | 单候选：`U+XXXX \t 字 \t IDS` |
| 4 | 3 389 | 双候选 |
| 5 | 106 | 三候选 |
| 6 | 6 | 四候选 |
| 7 | 1 | 五候选（实测该行是 `U+4E87 亇`） |
| **合计** | **88 937** | |

因此「同一码点只保留一条」在**行**层面天然成立；真正需要取舍的是**行内多列**选哪一列。

## 2. 实际采用的取舍规则

### 2.1 块 3（IDS 拆解表）

| 决策点 | 采用规则 | 理由 |
|---|---|---|
| 多候选取舍 | **取每个码点的第 1 个候选列（`parts[2]`）** | 见下方说明 |
| 结构符剥离 | 显式剔除 `U+2FF0..U+2FFB`、`U+2FFC..U+2FFF`、`U+31EF` | `So` 兜底会误删 984 处真部件（⺼⺊⺀㇉…），见 §1.1 |
| 来源标记 | 剥离 `[GJK]`/`[T]`/`[U]` 等方括号标注后再剥离结构符 | 标注不是部件 |
| 递归深度 | **只做一层，不递归** | 用户明确要求；`comps` 中允许残留可继续拆的合成字 |
| 不可拆条目 | **不写入**（无结构符 / 去符后为空 / 去符后等于该字本身） | FORMAT §5 允许 `compLen==0` 条目存在，但无写入价值；读取端视同不存在 |
| 排序 | 按 `codepoint` 严格升序，无重复 | FORMAT §5 硬约束 |
| 含 `?` `*` `&` `U+` 的候选 | 丢弃 | 防御规则；实测本数据源 0 条触发 |

**关于「取第一条」的选择**：任务书给出的是「优先 `unicode` 来源，其次按文件出现顺序取最后一条，
无法判断来源就取第一条」。但实测发现：

1. **没有独立的「来源」字段**。第 1 列是码点、第 2 列是字、第 3 列起全是 IDS 候选，
   `[T]`/`[G]`/`[J]`/`[K]`/`[V]` 是**字形来源地区缩写**（台湾/中国大陆/日本/韩国/越南），
   `[U]` 出现 91 次。这些标记**不是**「越新越权威」的排序，而是**地区字形差异**。
2. `[U]` 标记的候选**几乎总在第 3 列（第一位）**，而不是最后一位——「优先 unicode 来源」与
   「取最后一条」在本数据源上互相矛盾。
3. 「取最后一条」会带来 **3 368 个码点**的差异，其中相当一部分是拆得更碎的候选
   （如 `丰`：第一条 `⿻三丨` 比最后一条 `⿻丿⿻二丨` 更简单直接）。

综合考虑「一级拆解的可用性」（部件越简单越好，便于输入法做部件级编码）以及**确定性**
（不依赖启发式判断），选择**取第一条**。该策略已由二进制产物反向验证：
`xingbian.bin` 的 88 480 条 IDS 与「取第一条」**100% 一致**（与「最后带标记」一致 85 440、
与「取最后一条」一致 85 112）。

### 2.2 块 2（词表）

**读音来源优先级**（与任务书一致）：

| 优先级 | 来源 | 说明 |
|---|---|---|
| 1 | `luna_pinyin.dict.yaml` 词条 | 自带音节序列，最可信 |
| 2 | `phrase-pinyin-data.txt` | 带调拼音，归一化后按空格切 |
| 3 | 单字表逐字拼接 | **仅在「长度 1~4 字」且「每个字的归一化读音唯一」时**才允许 |

**多音字处理：宁缺毋滥。** 逐字拼接时若任一字在单字读音表中归一化后仍有多个候选
（如 `的` = `de`/`di`、`了` = `le`/`liao`、`明` = `ming`/`meng`），**则丢弃该词**，
绝不猜测。实测本数据源下 `你/妈/尼/玛/好/测/试/谢/意/影/键/盘/国` 均为归一化后唯一。

**拼音归一化**：

- 去调、全小写、只保留 `a-z`。
- **`ü` 映射选择 `v`（不是 `u`）**。理由：`luna_pinyin.dict.yaml` 本身就用 `v`
  （实测 `女 nv`），`v` 是 Rime/主流输入法的事实标准，且能与 `u` 明确区分以避免
  「女 nv」与「怒 nu」碰撞。
- 映射表（完整覆盖）：
  `āáǎà→a`、`ēéěè→e`、`īíǐì→i`、`ōóǒò→o`、`ūúǔù→u`、`ǖǘǚǜü→v`、`ńňǹ→n`、`ḿ→m`。
  实现上先做 `ü` 系列→`v`（必须在去组合符之前，否则 `ü` 会退化成 `u`），再走 NFD 去组合符。
- 另作防御：`u:` / `uu` → `v`；数字调后缀（`pin1`）剥除；归一化后不匹配 `^[a-z]+$` 的读音丢弃
  （实测仅 **1** 条被丢弃，来自 `phrase_pinyin`）。

**词的过滤规则**：

- `wordLen >= 1`、`sylLen >= 1`、**`sylLen == wordLen`**（纯汉字词，音节数与字数相等）。
- 只保留汉字：`0x4E00-0x9FFF`、`0x3400-0x4DBF`、`0xF900-0xFAFF`、`0x20000-0x2FA1F`、`0x3007`。
- 不得含 `\t`/`\n`。
- 同一词**允许多条不同读音**（读取端合并）。
- `freq >= 1`。
- **繁→简归一化**：在裁剪前用 OpenCC `TSCharacters` 逐字把繁体词归一化为简体，
  归一化后相同的条目合并、`freq` 取最大值。实测 `薴→苧→苎` 存在 1 条链，故迭代到不动点。

**频次模型**：`freq = max(1, round(1_000_000 × max over sources(贡献)))`，其中
essay 权重 1.00（按 `log1p(freq)/log1p(1 512 483)` 归一）、jieba 权重 0.90
（按 `log1p(freq)/log1p(883 634)` 归一）、luna 词条平值 0.28、phrase-pinyin 平值 0.23、
pinyin-data 单字平值 0.03、种子词（你妈/你好/中国）平值 0.96。

### 2.3 音节表（块 1）

由**词表实际用到的音节**重新编号：去重 → 按**字节序升序**排序 → 行号即音节 ID →
最后一行**不带** `\n`。

### 2.4 块 4（Meta）

UTF-8 JSON，键按 `sort_keys=True`、分隔符 `(",", ":")`。含 14 个顶层键：
`blocks_sha256`、`format`、`format_version`、`generated_at`、`generated_at_policy`、
`generator`、`normalization`、`reading_priority`、`reproducibility`、`source_contrib`、
`source_files`、`spec`、`stage_stats`、`trimming`。

`generated_at` 采用**确定性时间戳**（`SOURCE_DATE_EPOCH` 优先，否则取源文件 mtime 最大值），
运行耗时只打印不写入，以保证同一批输入重复构建产出**逐字节相同**的产物。

> ⚠️ **本小节初版曾给出一个技术性理由，该理由已被实测证伪，现予撤销。**
> 初版原文：「若仍卡在 15 万，会出现『简体词已合并进来但又被裁掉』的回归」。
> 用 `--max-words 150000` 构建隔离产物后实测**不可复现**（详见 §7，并由 §6 作者独立复算）：
>
> | 复核项 | 实测 |
> |---|---|
> | 150 k 版本自检 | **15/15 通过**，`SELFTEST PASS`，退出码 0 |
> | 16 个验收词在 150 k 中 | **全部存在**，`freq` 与 200 k **逐值相同** |
> | 150 k 相对 200 k 被裁的唯一词 | 49 872 个，`freq` 全部落在 **426 961 ~ 442 287**（全表最低档） |
> | 被裁词中经 T→S 会改变的（繁体残留） | **0** |
> | 词表繁体残留（150 k / 200 k） | **0 / 0** |
>
> 结论：**归一化已经在两个规模下都彻底消除了繁体词**，
> 「简体词被裁掉」的回归**不存在**。因此 200 k 的收益只是「多覆盖 49 872 个最低频词」
> （体积 +966 KB），**不是正确性问题**。
>

> 硬性验收（16 词 + 5 条第一名）同样全部通过。当前默认值保持 200 000，
> 因为这是任务书的明确要求；规模取舍的最终裁决权在任务负责人。

## 6. 修复记录：繁 → 简归一化（2026-10-16）

### 6.1 缺陷现象（修复前实测）

用独立脚本读回旧产物 `assets/build/xingbian.bin`（130 000 条版本）实测：

| 音节序列 | 修复前候选（词, freq） |
|---|---|
| `ni ma` | `你媽`(571713), `尼瑪`(567730) —— **`你妈` 根本不在词表里** |
| `jian pan` | `鍵盤`(636297) —— `键盘` 不在 |
| `shu ru fa` | 无 `输入法` |
| `zhong guo` | `中國`(848360), `中国`(773754) —— 繁体排第一 |
| `ce shi` | `測試`(737661), `测试`(512834) —— 繁体排第一 |
| 存在性 | `你妈` = False；`键盘` = False；`输入法` = False；`形变` = False |

**根因**：`essay.txt`（Rime 繁体八股文词频）给的频次极高（实测 max 4 822 928，
远高于 `jieba_dict.txt` 的 883 634），而繁简两套在候选表里是**各自独立的条目**，
从未合并。归一化前的频次公式 `freq = round(1e6 × max_over_sources(contrib))` 下，
繁体词的 log 归一化贡献压过简体高频词，且两者抢占同一份 13 万名额，
导致「简体常用词被繁体同形词挤掉」——**这正是本产品最致命的缺陷**，
因为目标用户是简体用户，且产品核心示例就是 `你妈 → 亻尔 女马`。

关键数据：`你妈` 在 `essay.txt` 与 `jieba_dict.txt` 中**都不存在**；
它只能由 `essay.txt` 的繁体 `你媽`（freq 3411）经 T→S 归一化后产生。
同理 `键盘`/`输入法`/`测试`/`中国`/`谢谢`/`电影`/`发展` 等的简体写法均不在 `essay.txt` 中。

### 6.2 OpenCC 映射表实际格式（勘察结论，与常见假设不同）

`assets/raw/opencc_TSCharacters.txt`（104 520 B）**不是空格分隔，而是 TAB 分隔**：
键与值之间是 `\t`，值侧多个候选之间才是空格。文件头注释原文：

```
# Open Chinese Convert (OpenCC) Dictionary
# Format: key	value(s) (values separated by spaces)
# Used in configs: hk2s.json, t2s.json, tw2s.json, tw2sp.json
```

实际数据行（前几行）：

```
㑮	㑮 𫝈
㑯	㑔
㑳	㑇
㑶	㐹
```

实测统计：

| 指标 | 实测值 |
|---|---|
| 总行数 | 5 062 |
| 非注释数据行 | 4 148 |
| 不同键 | 4 148 |
| **恒等映射**（键 == 首个候选，如 `㑮 → 㑮`） | 927 |
| **真繁体**（键 != 首个候选） | **3 221** |
| 多候选行（>1 个简体） | 997 |
| 首个候选为非 BMP 的键 | 227 |
| 键或值为多字符 | 0 |
| 映射链（一个字的简体写法仍是繁体键） | 1 条：`薴 → 苧 → 苎` |
| 环 | 0 |

文件中间还夹有 `# @tofu-risk: ...` 审计注释（提示某些字不被基线字体覆盖），
与普通 `#` 注释一并跳过。

> **勘察发现的最重要一点**：927 行是**繁→繁恒等映射**。若把映射表的全部键都当「繁体字」，
> 会在自检里产生大量误报（`㑮`、`㑯` 这类字本身就是自己的简体写法）。因此
> 「是否繁体」的判定必须是 `键 != 首个候选`，这一点在 §6.5 第 14 项自检里显式实现。

### 6.3 修复方案

在 `tools/build_dict.py` 中新增 `parse_opencc_map()` / `opencc_first_map()` /
`to_simplified()` / `normalize_t2s()` 四步，插在「候选词条构建完成」与「裁剪」之间：

1. **解析**：按 `\t` 切分、跳过 `#` 注释；每个键保留候选列表，取**第一个**候选建 `t2s` 首候选表。
2. **逐字映射**：`to_simplified(word, t2s)` 对词内每个字做 `t2s.get(c, c)[0]`，
   **映射表里没有的键原样保留**（已经是简体的词一字不改）。
3. **不动点迭代**：因为存在 `薴 → 苧 → 苎` 这条链，单趟映射会留下 `苧` 这个真繁体字，
   使 §6.5 第 14 项自检误报。故迭代到不动点（上限 8 趟，实测 2 趟内收敛）。
4. **合并**：同一 `(音节 ID 序列, 简体词)` 的条目合并，`freq` 取 **max**。
   繁简单字一一对应 ⇒ 词长与音节序列长度不变，**不重算拼音**。

两个**有意为之**的取舍：

- **不合并非同音异形词**：合并键含音节 ID 序列，`你妈`(ni ma) 与 `尼玛`(ni ma) 音节序列
  相同，但词形不同 —— OpenCC 不会把 `尼` 映射成 `你`，故二者保持为**独立条目**，
  修复后 `ni ma` 的两名候选是 `你妈`(960000)、`尼玛`(567730)，都保留。**没有丢词**。
- **不丢弃非 BMP 条目**：早期实现曾在归一化阶段丢弃 18 013 条含非 BMP 字的词条，
  这会把「已经是简体的词」一并删掉（如 `𨱵`、`𠈬`），与「映射表里没有的键就原样保留」
  的要求直接冲突，且旧产物默认保留这些生僻字（属于功能倒退）。已改为**保留**，
  仅统计不丢弃（`entries_kept_astral`）。
  FORMAT §4 的 `wordLen` 是 **UTF-16 码元数**、`sylLen` 是**码点数**，二者对非 BMP 词
  本来就不等，写读两端都已按此处理，**格式未变**。

且 `docs/FORMAT.md` §7 的「建议 8 万 ~ 15 万」是**规模参考**而非格式硬约束
（格式只要求 `count` 可被正常回读）。实测体积 4.17 MB、构建 15.33 s、内存可控（自检第 9 项要求 < 25 MB）。

> ⚠️ **一个曾被写在这里、但已被证伪的理由**：初版曾称「若仍卡 15 万会出现

3. **未逐条人工核对字形的语言学正确性。** 「无真繁体字残留」是**集合意义**上的判定

4. **多音字归一化后的读音未复核。** 归一化只改字形、不重算拼音（依据是繁简单字一一对应），

### 7.3 §3.4 第 1 条理由经实测**不成立**

§3.4 原文：「若仍卡在 15 万，会出现『简体词已合并进来但又被裁掉』的回归
（**这正是归一化想要解决的问题本身**）」。

实测反证：把 150 k 相对 200 k **被裁掉的 49 872 个词**全部取出后判定——

| 判定 | 结果 |
|---|---|
| 被裁词的 `freq` 区间 | **426 961 ~ 442 287**（全部落在全表最低一档；150 k 的 `min_freq_kept_multi` = 442 287，两档严丝合缝相接） |
| 被裁词中含**真繁体字**的数量 | **0** |
| 被裁词经 T→S 转换后会与 200 k 中某词撞车的数量 | **0** |
| 词表（150 k 与 200 k）中繁体残留词总数 | **0 / 0**（两版本均为 0） |

判定口径是**定义性**的：对词表每个词做完整 T→S 转换，`T2S(word) != word` 即判为繁体残留。
对照表用 `opencc_TSCharacters.txt`，实测 4 148 键。
即：**繁体词在两个规模下都已经被归一化彻底消除，15 万并没有「把简体词裁掉」**，
§3.4 描述的回归**不可复现**。

### 7.4 200 k 的真实代价与收益（供裁决用）

- 200 k 比 150 k 多出的 49 872 个**唯一词**，`freq` 落在 **426 961 ~ 442 287**
  （平均 435 065），即全表最低频段——不是「被错误丢弃的重要词」。
- 这些词贡献的 `freq` 总和占 200 k 总频次的 **26.19 %**。
  该数字看起来大，但源于 `freq` 本身在小范围内的长尾堆积（该频段每词 `freq` 几乎相同），
  **不能据此认为它们与高频词同等重要**。
- 代价：产物 +966 KB（3.25 → 4.27 MB）、内存 +约 26 %。
- **结论：规模选择是「体积/内存」与「长尾覆盖」的取舍，不是正确性问题。**
  两个规模都通过全部自检与独立校验，任务负责人可任选；

### 8.7 第 14 项的豁免是**真修复**还是**放宽测试**? —— 独立复算结论：真修复

## 9. 元信息 `counts.blocks` 缺陷与修复（第三方 agent 追加，2026-10-16 17:41）

### 9.1 缺陷现象（实测，不是推测）

任务书 §4 要求 Meta 至少含 `counts`。该键在 §8 记录的版本里**自相矛盾**：

```
文件头 blockCount          = 4
Meta.counts.blocks         = 3      <-- 不一致
```

- 定位：`tools/build_dict.py:1805-1810` 的 `"counts": { ..., "blocks": len(blocks) }`。
- 根因：`blocks` 字典在 `build_dict.py:1706-1709` 只装了块 **1/2/3**；
  块 4（Meta）直到 `build_dict.py:1839` 才被写入 `blocks[BLOCK_META]`，
  而 `meta` 字典在 `build_dict.py:1805` 就已经定稿 —— **`len(blocks)` 在 Meta 自身入表之前求值**，
  必然少算 1。
- 影响面：**仅 Meta 的自述字段**。文件头 `blockCount=4`、目录 4 项、以及
  `build_dict.py:1017` 的写盘逻辑（按 `BLOCK_IDS_ORDER` 取）都正确，
  产物**格式完全合规**，读取端不依赖 `counts.blocks`。
  这是**元信息说谎**，不是数据损坏 —— 但足以误导维护者，故按缺陷处理。

### 9.2 修法

```python
# build_dict.py:1805-1813 (修复后)
"counts": {
    "syllables": len(syllables),
    "words": len(entries),
    "ids": len(ids_table),
    # 注意: 此处不能用 len(blocks) —— meta 本身在下面几行才写入 blocks[BLOCK_META],
    # 用 len(blocks) 会得到 3 而文件头 blockCount 是 4, 自相矛盾.
    "blocks": len(BLOCK_IDS_ORDER),
},
```

去掉对求值时序的隐式依赖，改用静态常量 `BLOCK_IDS_ORDER`（`build_dict.py:86`，长度恒为 4）。
